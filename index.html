About Me

Java·Spring으로 ERP와 공공기관 웹 서비스를 3년 넘게 개발하고 운영했습니다. 두 명이서 회사의 모든 물류가 거쳐 가는 ERP를 새 시스템으로 옮기고 고도화했고, 이후 운영까지 맡으며 "멈추지 않고 돌아가는 서비스"가 무엇인지 배웠습니다.

2026년에는 SK네트웍스 Family AI 캠프에서 데이터 수집, 머신러닝, RAG, 멀티 에이전트 서비스를 다섯 번의 팀 프로젝트로 만들었습니다. 최종 프로젝트에서는 정부지원사업 공고 데이터 파트를 혼자 맡아 매일 도는 수집 배치, 검색과 자격 판정, AWS 배포까지 책임졌습니다.

모델 성능만큼 서비스의 안정성과 비용을 함께 봅니다. AI 도구를 적극적으로 쓰되 결과는 테스트와 평가로 검증하고, 쓰지 않기로 한 기술도 그 이유를 기록으로 남깁니다.

01

S-Brain

창업 아이템에 맞는 정부지원사업을 찾아, 사업계획서까지 만들어 주는 멀티 에이전트 서비스

  • 2026.08 – 2026.10
  • 팀 5명
  • Data & Matching 담당 (공고 데이터·매칭 파트 단독 개발, 인프라·배포 공동)

문제

정부지원사업 공고는 여러 기관에 흩어져 있고, 지원 자격은 첨부 문서(PDF·HWP) 안에 숨어 있습니다. 그래서 창업자가 사업계획서를 다 쓴 뒤에야 자격이 안 된다는 걸 알게 되는 일이 생깁니다.

내가 한 일

  • 공고 수집 파이프라인 구축 — 공공 API 2곳에서 공고를 모아 정규화하고, PDF·HWP 첨부 본문 추출 → 임베딩 → LLM 자격 판정까지 14단계를 매일 자동으로 실행했습니다 (cron·systemd).
  • 매칭 검색 설계 — 지역·업력·사업자 유형 같은 정형 조건으로 먼저 거른 뒤, 의미 검색과 BM25를 RRF로 합친 하이브리드 검색으로 순위를 매겼습니다. 개인사업자·법인이 신청할 수 없는 공고는 차단하고, 원문 대조를 마친 공고만 가산점을 반영했습니다.
  • 팀 서비스 연결과 배포 — 조율 에이전트가 호출하는 HTTP API 4개를 설계했고(연결 시험 16/16 통과), AWS CloudFormation 스택과 한 번에 올리고 내리는 배포 스크립트를 작성했습니다.
  • 평가 체계 구축 — 평가 질의 58개, 판정 1,617쌍으로 평가셋을 만들어 개선 전후를 측정했습니다.
  • AI 도구를 활용한 개발과 교차 검수 — Claude·Codex로 구현하고, 다른 모델이 서로의 결과를 검수하는 방식으로 품질을 관리했습니다. 검수 요청·결과·재확인을 모두 문서로 남겼습니다.

02

PetTriage

반려동물이 무언가를 먹었을 때, "지금 병원에 가야 하나?"에 근거와 함께 답하는 AI

  • 2026.07 – 2026.08
  • 팀 4명
  • 백엔드 (3차) → AWS 배포 담당 (4차)

문제

반려동물이 초콜릿이나 포도를 먹었을 때, 보호자는 인터넷의 엇갈린 정보에 기대게 됩니다. PetTriage는 진단 대신, 근거 자료를 찾아 지금 해야 할 행동을 4단계(응급 · 지금 연락 · 곧 방문 · 관찰)로 알려 줍니다. 원칙은 "RAG가 근거를 찾고, 코드가 등급을 정하고, LLM은 그 위에서만 말한다"입니다.

내가 한 일

3차 — 서비스 백엔드 (FastAPI)

  • 계정·반려동물·다이어리 API와 DB 설계 — 회원가입·로그인(JWT)과 반려동물 프로필 API를 처음 구현했고, 다이어리를 메모리 저장에서 DB 영구 저장으로 바꿨습니다. 이때 만든 "하루 1건" 저장 방식은 팀 설계 결정으로 기록됐습니다.
  • LangGraph를 채팅 API에 연결 — 질문 분류(LLM이 실패하면 키워드로 대신 분류), 종·물질·체중·섭취량 추출, 근거 검색 노드를 구현했습니다. /api/ask에 그래프 엔진을 연결하고, 대화 이력 저장이 실패해도 답변은 나가도록 했습니다.
  • 근거 자료 수집 — 자유롭게 쓸 수 있는 학술·공공 자료를 확보했습니다. 이 자료가 독성 기준 수치의 주된 출처가 됐습니다.

4차 — 웹 전환과 AWS 배포 (Django)

  • AWS 배포 — ALB와 ACM 인증서로 HTTPS를 적용하고, EC2의 nginx가 Django와 FastAPI로 요청을 나눠 보내도록 구성했습니다. 외부에는 80·443 포트만 열고, systemd로 재부팅 후 자동 실행되게 했으며, 도메인 연결까지 마쳤습니다.
  • 채팅·다이어리 화면 Django 전환 — 3차의 토큰 인증 화면을 세션 인증으로 바꾸고, 공통 레이아웃과 사이드바를 만들었습니다.
  • 산출물 — AWS 배포계획서, 요구사항정의서(52건)를 작성했습니다.

어려웠던 점 — 배포 직후 HTTPS 요청이 400 오류로 거절됨

문제
배포를 마치고 HTTPS로 접속하자 요청이 400 Bad Request로 거절됐습니다.
원인
nginx 기본 프록시 설정과 팀 프록시 설정이 함께 적용되면서 같은 헤더가 두 번 붙었습니다.
해결
공통 프록시 설정을 파일 하나로 통일했습니다. 원래 접속 방식(https)은 로드밸런서가 넘긴 값을 그대로 전달했는데, nginx 기준 값을 쓰면 무한 리다이렉트가 나기 때문입니다. 대신 바깥에서 이 값을 위조하지 못하도록, 80 포트는 로드밸런서에서만 들어올 수 있게 보안그룹을 설정했습니다.
그 밖에
상태 검사가 302를 받던 문제(검사 경로를 200을 주는 로그인 페이지로 변경), CSRF 403 오류, 가용 영역 연결 누락도 하나씩 원인을 찾아 해결했습니다.

Signal-T

통신사 고객의 이탈을 예측하고, 로컬 LLM이 고객 유지 전략을 제안하는 서비스

  • 2026.06
  • 팀 5명
  • 백엔드·모델 학습 담당

문제

통신사는 가입자가 떠날 때마다 새 고객을 모으는 마케팅 비용이 커집니다. Signal-T는 떠날 위험이 큰 고객과 옮겨 갈 통신사를 미리 예측하고, 붙잡을 전략까지 제안합니다.

내가 한 일

  • 이탈 예측 모델 학습 — KISDI 한국미디어패널조사(2010~2024년, 118,336건)로 파생변수 5개를 만들고, 전처리와 XGBoost를 하나의 학습 파이프라인으로 묶어 저장했습니다.
  • 예측 서비스 백엔드 — 모델을 한 번만 불러와 재사용하고, 한 명씩 또는 CSV·엑셀 파일로 여러 고객을 한꺼번에 예측하는 기능을 만들었습니다.
  • 로컬 LLM 분석 — 일괄 예측 결과를 요약해 프롬프트로 만들고, 로컬 LLM(EXAONE 3.5)이 고객 유지 전략을 실시간으로 작성해 보여 주도록 연결했습니다. 외부 API 없이 사내에서 돌릴 수 있는 구조입니다.
  • 로그인 흐름 — 아이디·비밀번호 1차 인증 뒤 얼굴 2차 인증으로 이어지는 로그인·회원가입 화면 흐름을 구현하고, 얼굴 인식 모듈과 연결했습니다.
